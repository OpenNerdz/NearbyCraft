# Nearby Craft and 7 Days to Die review — 19 September 2026

This is the **pre-update 1.2.0 review**. The subsequent 1.3.0 implementation and installation are described in [README.md](README.md); remaining live-game acceptance checks are in [TESTING.md](TESTING.md). The findings and original review results below are retained as a historical snapshot.

Nearby Craft loads and builds on the installed game, but it has confirmed presentation and storage-selection defects, plus inventory-consistency risks that should be addressed before expanding its multiplayer use. There is no evidence in the inspected logs of a general frame-rate regression caused by Nearby Craft.

This was a source, binary, configuration, packaging, and historical-log review. No game session was launched, no save was altered, and no fixes or extra mods were installed. Findings described as risks were identified by tracing the code; item loss and multiplayer conflicts were not reproduced in a live game.

## Findings, ordered by repair priority

### 1. High: item transfers need a single, checked commit path

**Code-confirmed consistency risk; no live item-loss test performed.**

`StorageNetworkSession.ApplyDisplayChange` accepts any positive amount moved as success. It does not require that the entire requested amount was deposited or withdrawn, nor restore the player's held stack on a failed or partial operation. `XUiC_StorageTerminalGrid.HandleSlotChangedEvent` then stores the requested display state even when the backend did not apply it.

The installed game's ordinary stack-merging and partial-pickup handlers change the UI/cursor as part of that operation. Some of those handlers are inherited by the custom terminal. Consequently, a stale display or a source becoming unavailable can leave the cursor/display and actual storage disagreeing. The carefully written `TrySwap` path does not cover every inherited interaction.

The crafting path has a related robustness gap: `StorageIndex.RemoveItems` ignores the amount returned by `RemoveFromStorage`. The game queues the craft before calling removal. A freshly rebuilt cache reduces stale-state exposure but is not a commit guarantee.

**Recommended repair:** make all transfer paths validate and commit the complete operation, reconcile the cursor using the actual committed result, and refresh after rejection as well as success. Craft consumption should either fully succeed or leave both ingredients and queue unchanged.

Evidence: [display-change handling](src/StorageNetworkSession.cs#L503), [grid callback](src/StorageTerminalUi.cs#L420), [craft removal](src/StorageIndex.cs#L209). Compared with installed `XUiC_ItemStack.HandleStackSwap`, `HandlePartialStackPickup`, and `ItemActionEntryCraft.OnActivated`.

### 2. High for multiplayer: storage edits are not coordinated through the game's lock workflow

**Architectural risk confirmed by source and installed-game inspection; no two-client test performed.**

The mod edits local storage arrays and calls `SetModified()`. In this game version that sends serialized tile-entity state. Normal storage access goes through the game's lock workflow. The mod does not acquire equivalent locks for connected storage or submit a server-controlled inventory transaction.

`IsUserAccessing()` checks are useful filters, but they do not reserve a container across clients. Two terminals or simultaneous crafting can work from different snapshots. Installing the same DLL on the server and clients does not itself coordinate those changes. Vehicles and drones also lack an equivalent in-use exclusion in the mod's entity-source scan.

**Recommended repair:** coordinate inventory mutations on the server using the game's locking model or a validated server transaction, with acknowledgements and rejection handling. Until that is verified, the README's multiplayer instructions should not be interpreted as evidence of multiplayer safety.

Evidence: [terminal deposits and withdrawals](src/StorageNetworkSession.cs#L273), [craft synchronization](src/StorageIndex.cs#L594), [entity sources](src/StorageIndex.cs#L463). Compared with installed `TileEntity.setModified`, `TEFeatureStorage` locking callbacks and `NetPackageTileEntity`.

### 3. Medium: the terminal includes land-claim storage that crafting deliberately excludes

**Confirmed by code and vanilla block definitions.**

The crafting index rejects `TEFeatureLandClaim`. The terminal scan does not. In V3.2 the land-claim block contains a `TEFeatureStorage` with a 7×4 inventory, and an owned composite storage reports itself as player storage. It therefore qualifies for the terminal's scan.

This can route ordinary deposits into the land-claim inventory, or expose its contents as ordinary network stock. Crafting then excludes that same inventory, making some deposited materials unavailable to Nearby Craft and creating inconsistent container counts.

**Recommended repair:** use a shared eligibility policy and explicitly exclude land-claim internals from the terminal. Check whether any items have already been deposited there before changing visibility.

Evidence: [terminal eligibility](src/StorageNetworkSession.cs#L119), [crafting exclusion](src/StorageIndex.cs#L422), vanilla `blocks.xml` line 1636 and `loot.xml` line 10467.

### 4. Medium: the localization file has the wrong extension for V3.2

**Confirmed compatibility defect.**

The package supplies `Config/Localization.txt`. The installed game's `Localization.LoadPatchDictionaries` checks specifically for `Config/Localization.csv`; it has no `.txt` fallback in that method. None of the inspected logs records loading NearbyCraft localization.

The Storage Network Console's localized item name and description are therefore skipped. The terminal's hard-coded window title can still look correct, which conceals the packaging problem.

**Recommended repair:** package the existing CSV content as `Localization.csv`, then check the recipe, creative inventory, placed-block name, and description in game.

Evidence: [packaged localization](package/Config/Localization.txt#L1), installed `Localization.LoadPatchDictionaries`.

### 5. Medium: the terminal auto-focus label emits real XUi errors

**Confirmed in existing play logs and current code.**

The `terminal_autofocus_color` binding returns `[green]` or `[disabledLabelColor]`. Those style tokens are not being resolved when returned dynamically to the label's colour attribute. The game logs a conversion failure instead.

There are **57 matching terminal colour errors** across the two substantial v1.2.0 sessions on 17 September: 13 in `00-19-53`, and 44 in `00-39-56`. The most recent launch logs do not show the error because they do not record opening the terminal.

**Recommended repair:** return a concrete XUi colour value or a correctly formatted resolved colour, following the already working nearby-crafting toggle's numeric colour approach.

Evidence: [binding](src/StorageTerminalUi.cs#L341), [label](package/Config/XUi_InGame/windows.xml#L24). First matching entry in `output_log_client__2026-09-17__00-39-56.txt` is line 856.

### 6. Medium: future patch mismatches log an error but still leave changed code active

**Confirmed robustness defect; no mismatch on installed V3.2 b10.**

The transpilers return their modified instruction lists even when the expected match count is wrong. `InitMod` also catches a patching exception without undoing any patches already installed. A future update could therefore leave availability, display and ingredient removal patched inconsistently.

**Recommended repair:** validate the required patch set before enabling the feature, restore the original instructions when validation fails, and remove this mod's partial patch set if initialization fails. Show one clear compatibility error.

Evidence: [availability validation](src/CraftingPatches.cs#L92), [consumption validation](src/CraftingPatches.cs#L140), [initialization](src/NearbyCraftMod.cs#L23).

## Additional improvement opportunities inside the mod

These are useful follow-up work, not demonstrated causes of poor FPS:

- **Batch synchronization per action.** `DepositBackpack` calls `Deposit` for each backpack stack, and each deposit marks changed containers independently. Since the game serializes tile entities when marking them modified, one deposit-all action can send the same container repeatedly.
- **Avoid repeated scans during one craft.** Each successful `RemoveFromStorage` invalidates the index; another required ingredient can immediately trigger another full nearby scan. Plan consumption once, apply changes, then invalidate once.
- **Refresh existing connections when their contents change.** The terminal listens for its own requested refreshes, but does not subscribe to changes from other users or automation. Use change notifications or a limited refresh of already-connected sources.
- **Preserve all vanilla movement restrictions.** Audit the custom shift-click, swap, and one-item handlers against `StackLock` and `CanMoveTo`, not only `CanPlaceInContainer`. These are separate checks in the installed game. This review did not establish every reachable special-item case.
- **Localize the remaining hard-coded English UI.** This is separate from fixing the ignored localization file.

## What the game logs actually show

Your long v1.2.0 session on 17 September contains **191 periodic FPS samples**, averaging **59.48 FPS**, with the lowest logged sample **51.18 FPS**. The configured cap is 60. These are periodic samples, not frame-time measurements or 1% lows; they cannot rule out brief stutters.

The earlier long session before NearbyCraft was loaded contains **213 samples averaging 59.51 FPS**. The scenes and workloads differ, so this is not a controlled benchmark, but the records do not support blaming NearbyCraft for a broad performance regression.

There are **nine chunk mesh queue-blocking warnings** across the logs, including four in that earlier session before the mod. Several resumed after roughly 1.0–1.3 seconds. These identify chunk-processing backpressure, not proof that the whole main thread froze for exactly that duration. They justify investigating travel/loading frame times, but not claiming a generic performance mod will fix them.

The latest log reports an i7-12700H, 16 GB RAM, an 8 GB RTX 3070 Ti Laptop GPU, Direct3D 11, view distance 5 and a 60 FPS limit. The current OptiScaler log reaches DLSS feature creation and reports DLSS v310.5.0. Its earlier `nvngx.dll not found` warning alone is not evidence that upscaling failed.

Other log observations:

- Discord connection retries occur repeatedly; two logs contain a Discord gateway error. If integration is unused, the game's own Discord setting is a reasonable way to reduce that noise. No measured FPS benefit is claimed.
- `E_XBL_NOT_INITIALIZED` appears during shutdown across all eleven logs, including before NearbyCraft. It is not evidence of an inventory bug or a crash caused by this mod.
- Two old `West Xuyofu Territory` save directories are reported without `main.ttw`. The active `New Narova Valley/Hard` save has both `main.ttw` and a `.bak`. This does not establish corruption of the active world, but makes reliable complete backups worthwhile.

## Recommended order

Fix the concrete localization, colour and land-claim selection defects, then make transfer/consumption handling consistent and verify multiplayer coordination before advertising that support. After that, smart deposit and reserve rules are the most natural additions to this mod. Complete save backups would be my first improvement outside it.

Before calling a repaired release verified, check normal crafting and cancellation, real inventory metadata, full-capacity handling, locked/excluded sources, and persistence after reopening the game. Multiplayer needs separate simultaneous-use and synchronization validation. None of those live verification results are claimed by this review.
